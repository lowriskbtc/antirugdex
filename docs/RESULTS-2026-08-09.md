## 🔴 NEW FINDING — the conservative `vault_spendable_amount` permanently strands 0.25% of the vault

**After `burn_unsold` completed, the token vault still holds 500,000,000,000,000 base units
= 500,000 whole ARD, and nothing can ever move them.**

SALE-PROGRAM.md's open item calls the conservative `vault_spendable_amount` an error
"strictly in the safe direction" whose practical effect is only *"fund the vault with a
little more than `supply_for_sale`"*. That understates it. The over-funding it forces is
not recoverable:

1. `11-sale-init.ts` moved 200,000,000 ARD in. The 25 bps fee took 500,000, so the vault
   read `amount = 199,500,000` with `withheld = 500,000` alongside it.
2. `vault_spendable_amount` computes `amount − withheld`, and `amount` is **already net**
   — so it subtracted the fee a second time and `supply_for_sale` was declared as
   **199,000,000**, one full fee below what the vault actually holds.
3. `burn_unsold` burns `supply_for_sale − total_claimed_tokens` — a **recorded-state**
   figure, not the vault balance. It burned 1 base unit and set `unsold_burned = true`.
4. That flag is one-shot (`require!(!sale.unsold_burned)`), and the vault is an ATA whose
   authority is the sale PDA. The program's only token-moving instructions are `claim`
   (all commitments settled) and `burn_unsold` (spent). **The 500,000 ARD is unreachable
   under the deployed program** — the same qualifier this repo insists on for Raydium, and
   for the same reason: the sale program's upgrade authority is a plain key, so an upgrade
   could add a path to it. `10-sale-status.ts` already prints that as a cannot-verify line.

**The script had no choice, and this is the part that fixes the blame correctly.**
`initialize_sale.rs:101` requires `vault_spendable_amount(vault) >= supply_for_sale`, and
that function returns `amount − withheld`. Declaring the true 199,500,000 would have been
rejected with `VaultUnderfunded`. `11-sale-init.ts` deliberately computes the same number
the program computes rather than grossing up and hoping — so the root cause is the Rust
helper, not the TypeScript that mirrors it.

Scale is structural, not incidental: it is always **one transfer fee of whatever is funded**
— 0.25% at the current rate. It is not lost principal, so the design invariant holds, but it
is permanently un-burnable supply in a vault that the "nothing is left with an authority"
story points at.

**The two candidate fixes as originally written — (a) was taken, (b) was not:**

- Fix `vault_spendable_amount` to `amount` alone (the measurement in SALE-PROGRAM.md already
  says this is correct), so nothing has to be over-funded. Needs
  `withheld_fees_do_not_count_as_supply` rewritten with it — that test is already flagged as
  passing for the wrong reason.
- Or have `burn_unsold` burn the **vault's actual balance** once all commitments are settled,
  rather than the recorded difference. Reaches the residue whatever caused it.

The first is the root cause; the second is a backstop that also catches accidental
over-funding. They compose.

**Why no test caught it — a coverage gap, not a limit of the harness.** A LiteSVM test
*could* find this: inject a vault, run the flow to the end, assert the vault balance is
zero. None does. Every existing test injects a hand-built vault balance and asserts on
transfers and recorded state, and **not one asserts what is left in the vault after
`burn_unsold`**. Worth adding as a test in its own right, since the fix should be provable
without a devnet run.

## Plan changes made during the run, and why

**The pool was NOT re-created** (handoff steps 2–3 skipped). `pool.devnet.json` already
recorded pool `6zKJcfzm…` with a real `lpBurnTx` and `lpSupplyAfterBurn: 0` — those steps
ran successfully on 2026-08-08. Re-running `06-create-pool.ts` would have **failed**, not
duplicated: a CPMM pool address derives from `(amm_config, mint0, mint1)`, so at config
index 0 the PDA for this mint pair is already taken. `mark_pool_created`'s own doc blesses
reuse — "A pool already trading is still accepted, and that is deliberate" — and its
`open_time` of 2026-08-08T00:10:37Z is in the past, so claims opened immediately.
Consequence: `POOL_OPEN_IN` never mattered and no second pool seed had to be fronted.

**The clock was narrower than the handoff implied, in a good way.**
`mark_pool_created` is the *only* remaining step with a deadline. Once `pool_created` is
true, `fail_on_missing_pool` is permanently blocked (it requires `!pool_created`), and
`claim`, `sweep_proceeds` and `burn_unsold` have no deadline at all. The critical path was
`finalize → mark_pool_created`, and after that the clock was irrelevant.

**`mark_pool_created` was simulated against the deployed program before sending.** Not
ceremony: the CPMM program id sits behind `#[cfg(feature = "devnet")]`, this project has
already been bitten by devnet-vs-default builds clobbering each other, and the IDL is
generated from a build rather than read from the cluster — so nothing on disk could prove
which binary was deployed. Simulation could, for free. It passed, confirming the deployed
artifact carries the devnet Raydium id. `14-mark-pool.ts` keeps that simulation as a
mandatory step, not an option.

`initialize_sale` accepted `supply_for_sale = 24,937,500` — the vault's **full**

## The deploy itself had to be verified by bytes

`anchor deploy` reported `DEPLOY_EXIT=1` **on a successful upgrade**: the upgrade
transaction confirmed (`5WL8b21c…`), and only the *IDL upload* afterwards failed, with
`Keypair file not found` for a file that demonstrably exists — anchor spawns that step under
CMD.EXE, which cannot handle the UNC path. The exit code and the log therefore prove
nothing about whether the deploy landed.

`verify-deploy.sh` settles it by dumping the on-chain program and comparing sha256 against
the local artifact (trimming the zero padding `solana program dump` adds):

```

non-zero bytes past the local length: 0
MATCH — the deployed program IS the locally built artifact.
```

### What this closes

**The stranding fix is proven end to end on a real validator.** The token vault went to
**exactly zero** — not one base unit left behind. Under the old formula this same run would
have ended with 62,500 ARD permanently out of reach, and `burn_unsold` already spent.

**`refund` has now run against a validator**, and behaved as designed: the bidder never
signed, the deployer paid the fee and received nothing, and the bidder gained exactly their
principal with no deduction. The `AlreadyClaimed` and `SaleNotFailed` guards were both
observed firing first — refund was attempted against a settled commitment and against a
still-`Bidding` sale, and refused with the right error each time.

**The withheld 62,500 is untouched and that is correct.** It was never sellable supply; it
belongs to the mint's withdraw-withheld authority and `harvest` is what moves it. A run that
drove the vault's withheld to zero would mean something had gone wrong, not right.

### Still never exercised on a validator

`fail_on_missing_pool` — the *other* route to `Failed`. It needs a third mint where the pool
deadline is deliberately allowed to lapse. Every other instruction has now run on chain.

Traps worth keeping:

- **`claim` needs 400k CU**, not the 60k a bid uses — `init_if_needed` ATA creation plus
  `transfer_checked` plus a system transfer plus the sysvar walk.
- **One claim per transaction.** `require_unbundled` rejects a second top-level instruction
  targeting this program. The ComputeBudget ix is a different program, so it is fine.
- **`token_program` is not IDL-pinned** on `claim`/`burn_unsold` — it must be passed as

- **Compare token deltas, not balances.** Bidder A is the deployer, whose ATA already held
  ~799M ARD; checking the post-claim balance against the expected net would "fail" by the
  entire pre-existing holding.
- **Bidder B needed SOL for ATA rent before claiming.** The refund arrives inside the same
  handler, too late to pay for the account it has to create first. B had 0.048 SOL and was
  fine; a bidder who commits everything would not be.
